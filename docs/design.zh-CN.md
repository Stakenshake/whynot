# 设计说明

这个工具为什么长这样。

## 问题

编码 agent 对上周发生的事没有记忆。每次会话都从零开始。这本身问题不大——代码就是状态，agent 可以自己读。但它读不到的是：**你为什么否决了某个方案。**

这类知识有三个麻烦的性质：

- 它不在仓库里，在某个人脑子里。
- 它会腐烂。半年后，那个人只记得「当时好像试过」，不记得具体哪里崩了。
- 重新发现它的代价很高。agent 会毫不心疼地再走一遍那条死路。

## 决定了整个设计的那个发现

我们记录了一条 2019 年的决策——「不要用 TypeScript，团队没人会」——然后让两个模型家族给一个 **2026 年的全新服务**做技术选型。**每一次回复都遵循了那条七年前的笔记。** 在提示词里加一句「这条很旧，请保持怀疑」没有修好。让条目过期，才修好。

完整数字见 [validation.zh-CN.md](validation.zh-CN.md)。

结论是：**不能指望 agent 正确地权衡一条陈旧指令。** 所以设计上干脆不要求它权衡——**过期条目根本不出现在 agent 的视野里。**

这一条决定了后面大部分设计。

## 四个决定

### 1. 数据是 git 里的 Markdown

其他一切都由此而来。

- 人不用工具也能读、能改。
- `git diff` 免费提供 review。
- `git revert` 免费提供撤销。
- 就算项目被放弃，数据依然能用 `grep` 检索。

这个领域里大多数工具把决策存进数据库或向量索引。那些项目死掉时，用户会连数据一起丢。这个项目从设计上就不允许这种事发生。

### 2. 默认过期

每条记录都带一个到期日。否决类 90 天，决策类 180 天，约束类 365 天。到期后，条目不再到达 agent。

过期条目**不会被删除**。`whynot stale` 会把它列出来，由人决定续期还是归档。两者都是显式动作。

`expires_on: never` 是为真正永久的约束准备的，但必须刻意写出来。**永久应该是一个决定，不是一个默认值。**

### 3. 不用 embedding，写入时不调模型

检索刻意做得很简单：对标题、标签、正文做大小写不敏感的关键词匹配，按命中的查询词数量排序。

两个理由：

- **可审计。** 当一条记录出现在 agent 的上下文里，原因一目了然：词对上了。用 embedding 的话，没人解释得清它为什么在那儿。
- **成本与失败模式。** 向量索引会过期。用 LLM 抽取记忆很贵，而且正是这类工具里记忆被污染的主要来源。这两样在这里都可以避免，所以就不做。

代价是真实的：关键词匹配会漏掉改写的说法。所以 `decisions_check` 在不带查询条件时会返回一个紧凑的索引，让 agent 先廉价地看到全貌，再往下缩小范围。

### 4. 没有工具时，格式依然可用

agent 通过 MCP 调用 `decisions_check`。如果 MCP 不可用，它仍然可以直接读 `.decisions/`——那不过是 Markdown。

这不是理论上的性质。在 Codex 集成测试里，MCP 调用被审批策略拦住了，agent 自动降级去读文件，并且**依然遵守了那条决策**。

## 形态：四层，不是一个

这个品类里一个常见的错误是选一种形态，然后把所有事都塞进去。这里的每件事属于不同的层：

| 层 | 形态 | 为什么必须是这个 |
|---|---|---|
| 数据 | git 里的 `.decisions/*.md` | 零工具依赖也能用。这是唯一不会死的资产。 |
| 行为 | `AGENTS.md` 里的一段指令 | 让 agent **主动记录**否决，是指令问题，不是 API 能力问题。 |
| 能力 | MCP server | 拉取式、结构化、跨 agent 通用。 |
| 人的回路 | CLI | 续期和归档是人的决定。 |
| 分发 | npm + agent 插件 | 零安装，在用户已经在的地方出现。 |
| **不是** | 托管 API | 关于代码库的决策是仓库里最敏感的东西。托管它就等于毁掉整个前提。 |

## 跨平台

目标平台是 Windows、macOS、Linux，因为三者的坑不一样。

- **换行符。** `init` 会往 `.gitattributes` 写 `*.md text eol=lf`。不写的话，Windows 上会写入 CRLF，每次 diff 都显示整个文件被改。
- **文件名。** Windows 禁止 `\ / : * ? " < > |`，而且 Windows 和 macOS 大小写不敏感。文件名会被 slug 成 `[a-z0-9]` 加中日韩字符，从根上消除一整类「Linux 上好的、换个系统就崩」的问题。
- **没有常驻进程。** Windows 的文件监听不可靠且需要原生依赖。工具只被调用，不常驻。
- **不用 git hooks。** 跨平台的 shell 在 hook 里是雷区。所以不用。

## 刻意不做的东西

- 向量检索 / embedding
- 写入路径上的任何模型调用
- 守护进程或文件监听
- Web UI
- 自动检测否决（以后可以用 hook，但核心闭环不依赖它）
- 团队同步。`git` 本身就是。
- 多仓库聚合

每一条都是真的有人要过的功能。每一条也都会让工具更重，而这个品类的坟场里全是更重的工具。

## 还没有答案的问题

- **真实使用中，重复犯错率真的会降吗？** 实验测的是单轮行为。真正重要的主张是长期的，而那个还没测。
- **过期多久会丢掉人还需要的信息？** 这是一个刻意的取舍，但比例未知。`whynot stale` 是它显现的地方。
- **团队用它撑得住吗？** 设计假设是一个人维护。五个人时，谁负责续期？
- **否决类 90 天合适吗？** 这是猜的。不同代码库的节奏不一样。
